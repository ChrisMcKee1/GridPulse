# Data Model – Ticket Management & Dispatch Optimization

This document decomposes the entities, relationships, and lifecycle rules introduced by the ticketing + dispatch feature. All new artifacts must live inside the Clean Architecture boundaries described in `specs/001-ticket-dispatch/plan.md` and respect both the API and UI lite constitutions.

## Entity Matrix

| Entity | Purpose | Key Fields | Relationships |
|--------|---------|------------|---------------|
| `Ticket` | Canonical outage work item tracked end-to-end. | `Id`, `OutageReferenceId`, `Status`, `Priority`, `AssignedCrewId`, `OpenedAt`, `ClosedAt`. | Owns many `AssignmentEvent` records; 1:many with `DispatchRecommendation`; optional 1:many with `CrewLocationSnapshot` via recommendations. |
| `DispatchRecommendation` | Snapshot of scoring results between a ticket and a candidate crew. | `Id`, `TicketId`, `CrewId`, `CompositeScore`, `ScoreComponents`, `IsOverride`, `OverrideReason`. | Many-to-one to `Ticket`; many-to-one to `Crew`. |
| `Crew` | Field crew roster entry w/ capabilities + workload. | `Id`, `DisplayName`, `Skills`, `CurrentTicketCount`, `Status`. | Links to current `CrewLocationSnapshot`; referenced by `Ticket` + `DispatchRecommendation` + `AssignmentEvent`. |
| `CrewLocationSnapshot` | Latest telemetry sample for a crew with quality metadata. | `Id`, `CrewId`, `Latitude`, `Longitude`, `CapturedAt`, `SignalAgeSeconds`, `IsStale`. | Many-to-one to `Crew`; optionally referenced by `DispatchRecommendation`. |
| `AssignmentEvent` | Audit trail entry for ticket workflow + crew actions. | `Id`, `TicketId`, `CrewId`, `EventType`, `Details`, `OccurredAt`, `Actor`. | Many-to-one to `Ticket`; optional `CrewId` for crew-specific events. |

## Entities & Fields

### Ticket

| Field | Type | Rules |
|-------|------|-------|
| `Id` | `Guid` | Generated by application service; primary key. |
| `OutageReferenceId` | `string` | Required; references ingestion pipeline identifier. |
| `Title` | `string` | Required; <= 140 chars for Blazor summary. |
| `Description` | `string` | Optional but recommended; persisted as text. |
| `Priority` | `TicketPriority` enum (`Critical`, `High`, `Medium`, `Low`) | Defaults from severity mapping; editable until `InProgress`. |
| `Status` | `TicketStatus` enum (`Open`, `InProgress`, `Resolved`, `Closed`, `Cancelled`) | Controlled via workflow service; only service can mutate. |
| `AffectedAssets` | `string[]` | Serialized JSON column; limited to 20 entries. |
| `CustomerImpact` | `int` | Number of customers out; autopopulated from ingestion. |
| `EtaMinutes` | `int?` | Calculated from assigned crew; null until dispatch ready. |
| `AssignedCrewId` | `Guid?` | Null until assignment; when set, must reference `Crew.Id`. |
| `AutomationSource` | `string` | `"ingestion"`, `"operator"`, etc. for analytics. |
| `AuditVersion` | `int` | RowVersion concurrency token. |
| `OpenedAt` | `DateTimeOffset` | Required. |
| `UpdatedAt` | `DateTimeOffset` | Auto-managed. |
| `ClosedAt` | `DateTimeOffset?` | Set when `Status` transitions to `Closed` or `Cancelled`. |

**State Transitions**

```
Open --(operator promote / auto rules)--> InProgress --(crew On Scene)--> Resolved --(operator verify)--> Closed
   \--(cancel)--> Cancelled
```

- `Open → InProgress`: requires dispatch readiness flag and at least one recommendation.
- `InProgress → Resolved`: only when crew posts completion event (`AssignmentEvent` type `CrewCompleted`).
- `Resolved → Closed`: operator confirmation; locks ticket (read-only edits).
- Any state → `Cancelled`: allowed before `Closed`; emits cancellation events.

## Relationships & Access Patterns

- `Ticket` ↔ `DispatchRecommendation`: `Ticket` aggregates zero-many recommendations per refresh cycle; only the most recent `CompositeScore` per `CrewId` is exposed to the dispatcher UI. EF configuration should enforce cascade delete of recommendations when a ticket closes.
- `Ticket` ↔ `AssignmentEvent`: append-only log ordered by `OccurredAt`; UI timeline component reads via ticket ID, optionally filtered by event type.
- `Crew` ↔ `CrewLocationSnapshot`: use `CrewLocationSnapshot` table keyed by `(CrewId, CapturedAt)` for history; `MockCrewTelemetryFeed` writes latest sample while archiving previous entries (nightly retention job can trim older than 72h).
- `Crew` ↔ `DispatchRecommendation`: combination unique index on `(TicketId, CrewId, CreatedAt)` prevents duplicate rows inside refresh window.

## Validation Rules & Derived Data

- Duplicate detection: before creating a ticket, search for Open/InProgress tickets sharing the same `OutageReferenceId` or overlapping geo bounds inside a 5-minute window; flagged duplicates add an `AssignmentEvent` of type `TicketDuplicateFlag` (extend enum if needed) and surface in UI.
- Telemetry freshness: mark recommendations as `IsStale=true` when their linked `CrewLocationSnapshot.IsStale` is true; dispatcher UI should block auto-assign.
- SLA metrics: maintain computed columns or materialized view for `TimeToDispatch` and `TimeToResolve` (difference between key `AssignmentEvent` timestamps). These feed reporting hooks in FR-011.
- RBAC projections: `TicketDto` includes minimal crew info (name, ETA, status) so UI does not expose restricted data.

## Enumerations

- `TicketStatus`: `Open`, `InProgress`, `Resolved`, `Closed`, `Cancelled`.
- `TicketPriority`: `Critical`, `High`, `Medium`, `Low`.
- `CrewSkill`: `HighVoltage`, `Underground`, `Distribution`, `Fiber`, `Transformer`, extendable via config.
- `CrewStatus`: `Available`, `Assigned`, `EnRoute`, `OnScene`, `Paused`, `Offline`.
- `AssignmentEventType`: see table above; extend when telemetry introduces new signals.

## Data Distribution & Persistence Notes

- PostgreSQL logical model should place ticketing objects into new schema `ticketing` (optional) or existing default; ensure indexes on `Ticket.Status`, `Ticket.Priority`, and GIST/GIN index on `AffectedAssets` for search.
- Telemetry feed writes happen every 60 seconds; use outbox table or `AssignmentEvent` channel to audit automation decisions.
- Future Cosmos DB migration: interfaces (`ITicketRepository`, etc.) abstract persistence to honor instructions in `azurecosmosdb.instructions.md`. Partition keys would prefer `OutageReferenceId` or `Region` to avoid hotspots.
